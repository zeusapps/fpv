# FPV

Betaflight configurations, hardware notes and setup guides for my FPV quads.

These are not source code. They are flight controller configuration backups (`diff all` dumps),
tuned variants of those, and the documentation needed to rebuild each aircraft from scratch.

Current state, outstanding work and open questions: **[HANDOFF.md](HANDOFF.md)**.

## Layout

```
docs/          shared Betaflight reference — CLI format, mode IDs, serial bitmask, OSD encoding
openspec/      specs and changes (OpenSpec)
radio/         transmitter-side setup, shared across the fleet
  README.md    widget install, telemetry, battery and link alarms, TX power
  CODE_REVIEW.md   review of the widget source
  WIDGETS/     mirrors the radio's SD card — copy to the card root as-is
<quad>/
  README.md    what this aircraft is, and the file index for it
  *.md         hardware, setup, binding, subsystem guides
  *.txt        tuned configs, ready to paste into the Betaflight CLI
  dumps/       raw `diff all` captures, including the untouched factory dump
```

## Conventions

- Tuned variants live in the quad's folder as `<QUAD>_<purpose>_V<n>.txt`
- Raw captures go in `dumps/`, named with the date they were taken
- **Never copy `mcu_id`, `signature` or `acc_calibration` between aircraft.** They are per-board.
  `acc_calibration` in particular must be regenerated by re-levelling on the actual airframe.
- **`radio/` never states a Betaflight value that differs between aircraft.** It links to the
  aircraft folder instead. The widget shipped with a README that gave one aircraft's GPS settings
  as though they were universal, and they were actively wrong for another — see
  [radio/README.md](radio/README.md).

## Things learned the hard way

Written up in full where they happened, collected here because they cost real time.

**[GPS and the DJI O4 share a pin on the Cube G4 board](pavo20-pro-ii/GPS_SETUP.md).** The board
routes the air unit's SBUS output to `RX1 (PA10)`. Soldering a GPS module's TX to that same pad puts
two push-pull drivers on one net. The GPS works perfectly with the air unit unplugged and produces
bit-corrupted NMEA the moment it is connected. BetaFPV's own GPS guide says to use UART1, but that
guide is written for a different board. Their 2025.12.5 release reorganised GPS onto UART2 for
exactly this reason.

**`GPS: connected` in `status` means nothing on the NMEA provider.** It reads true with the module
physically unplugged, because it is derived purely from the driver state machine and the NMEA path
advances without needing a single byte. The only honest indicators are a satellite count in the
Configurator GPS tab, or GPS elements appearing in the OSD.

**Betaflight omits GPS OSD elements entirely until `SENSOR_GPS` sets.** So "no GPS in the OSD" and
"GPS showing zeros" are completely different faults. Zeros means it is working and has no fix.

**An upside-down prop reads as a PID oscillation.** It still flies, and screams above about 35%
throttle. Check prop orientation before touching the tune.

**[An EdgeTX QR code is theme-coloured unless you say otherwise](radio/CODE_REVIEW.md).** The
GPSQR widget drew its code with no colours set. `lvgl.qrcode` defaults an unset `bgColor` to
`COLOR_THEME_SECONDARY3`, and an unset `color` to `COLOR_THEME_SECONDARY1` — both theme variables,
so on a dark theme the code can render dark-on-dark and no phone will read it. The widget's own
header comment claimed it "always stays black-on-white"; the code never did. A recovery tool that
displays something plausible and does not scan is worse than one that visibly fails, because you
only find out standing in a field.

## AI assistants

This repository supports Claude Code and Codex.
Open the repository folder in Codex. `AGENTS.md` directs Codex to the shared instructions in `CLAUDE.md`.
The repository includes OpenSpec skills in `.agents/skills/` for Codex and `.claude/skills/` for Claude Code.
Install the OpenSpec CLI if `openspec --version` fails:

```powershell
npm install -g @fission-ai/openspec
```

Use these commands with either agent:

| Task | Claude Code | Codex |
|---|---|---|
| Prepare a complete proposal | `/opsx:propose` | `$openspec-propose` |
| Explore a question | `/opsx:explore` | `$openspec-explore` |
| Implement a change | `/opsx:apply` | `$openspec-apply-change` |
| Revise a plan | `/opsx:update` | `$openspec-update-change` |
| Sync the main specs | `/opsx:sync` | `$openspec-sync-specs` |
| Archive a change | `/opsx:archive` | `$openspec-archive-change` |
| Prepare a proposal through the local alias | `/opsx:ff` | `$openspec-ff-change` |
| Start a change step by step | `/opsx:new` | `$openspec-new-change` |
| Create the next artifact | `/opsx:continue` | `$openspec-continue-change` |
| Archive multiple changes | `/opsx:bulk-archive` | `$openspec-bulk-archive-change` |
| Verify a change | `/opsx:verify` | `$openspec-verify-change` |
| Learn the workflow | `/opsx:onboard` | `$openspec-onboard` |

For example, use `$openspec-propose <description>` in Codex to prepare a change.
Use `$openspec-apply-change <change-name>` when you want to implement it.
The local `ff` alias follows the proposal workflow and stops after the artifacts are ready for review.

Codex setup references: [repository instructions](https://learn.chatgpt.com/docs/agent-configuration/agents-md)
and [repository skills](https://learn.chatgpt.com/docs/build-skills).
