# CLAUDE.md

Shared repository instructions for Claude Code and Codex. Codex reads this file through `AGENTS.md`.

## Start here

`HANDOFF.md` at the repo root records current aircraft state, what is verified versus untested,
outstanding work, and the findings that cost real time to establish. Read it before doing anything
with the Pavo20 Pro II.

## What this is

Betaflight flight controller configurations, hardware notes and setup guides for a small fleet of
FPV quads. The aircraft folders are **not source code** — nothing in them builds or has tests, and
the "build" is a human pasting a `.txt` file into the Betaflight Configurator CLI and flying the
aircraft.

One exception, added 2026-09-03: `radio/WIDGETS/GPSQR/main.lua` is Lua that EdgeTX executes on the
transmitter. It is still not buildable or testable here — there is no interpreter, no emulator and
no harness in this repo — but it is code, and it gets reviewed as code. `npx luaparse <file>`
catches syntax errors and nothing else; everything past that is read the API reference, walk the
arithmetic, then verify on the radio. `radio/CODE_REVIEW.md` is the record.

### Layout

One folder per aircraft, plus two shared folders:

- `docs/betaflight-reference.md` — read this before answering anything about CLI format, mode IDs,
  serial bitmasks or OSD position encoding.
- `radio/` — transmitter-side setup for the HelloRadio V12 MAX, which flies all three aircraft.

**The radio/aircraft split is load-bearing.** `radio/` must never state a Betaflight setting that
differs between aircraft; it links to the aircraft folder instead. The GPSQR widget arrived with a
README that gave one aircraft's GPS protocol and baud as though they were universal, and they were
the documented wrong answer for another — enough to break a GPS that currently works. The rule is
written as a spec requirement, not just a convention: see
`openspec/specs/radio/gpsqr-widget/spec.md`.

A setting that is genuinely identical on every aircraft (`report_cell_voltage`, say) may appear in
`radio/`, but as a step the user applies and confirms — never as an edit to a committed `.txt`.

## The stakes

These configs fly real hardware carrying spinning carbon props. A wrong value is not a failing
test — it is a crash, a burned motor, or an injury.

- **Never invent a setting name.** Verify it against the Betaflight source for the firmware version
  in use, or have the user run `get <partial_name>`, which prints the allowed values.
- **Never copy `mcu_id`, `signature` or `acc_calibration` between aircraft.** They are per-board.
  `acc_calibration` must be regenerated by re-levelling on the actual airframe.
- **Never invent PID numbers.** Prefer the manufacturer's published tune. If a change is genuinely
  needed, change one thing, say what to observe, and record it in a new versioned variant.
- A config from one cell-count variant will not run correctly on another.
- When a diagnosis is uncertain, say so and propose the measurement that would settle it. Several
  confident-sounding hypotheses in this repo's history were wrong; the hardware settled them.

## Verify against source, not memory

Betaflight behaviour is frequently counter-intuitive and changes between versions. Where a claim
matters, check the actual source at the user's version and quote it. Worked examples already in the
repo, all of which overturned a plausible wrong answer:

- GPS OSD elements are omitted entirely unless `sensors(SENSOR_GPS)` — `osd_elements.c`
- `SENSOR_GPS` sets on a parsed frame with **no fix required** — `gps.c`
- `GPS: connected` derives only from `gpsData.state >= GPS_STATE_CONFIGURE` — `cli.c`
- The UBLOX driver never leaves `DETECT_BAUD` without a `MON-VER` reply, so it needs a working
  FC→module TX line; the NMEA path advances unconditionally — `gps.c`

Useful sources: `betaflight/betaflight` for firmware, `betaflight/config` for board targets
(`configs/<MANUFACTURER>/<BOARD>/config.h`), and `build.betaflight.com/api/builds/<key>/json` to
see exactly which options a cloud build was compiled with.

## Working with config files

- Preserve the `batch start` / `defaults nosave` header and the `save` footer
- `profile_name` and `rateprofile_name` are capped at **8 characters**; exceeding it aborts the
  whole batch at `save`
- Inside a batch, one bad line means nothing is written. For experimental blocks, omit
  `batch start` so a single rejected line does not block everything else
- Tell the user to paste in chunks — the Configurator CLI drops lines from large pastes

## OpenSpec

This project uses OpenSpec. Specs live in `openspec/specs/`, changes in `openspec/changes/`.
Both agents have 12 OpenSpec workflows: propose, explore, apply, update, sync, archive, ff,
new, continue, bulk-archive, verify, and onboard.
Claude Code commands live in `.claude/commands/opsx/`, with skills in `.claude/skills/`.
Codex skills live in `.agents/skills/`.

Start a change with `/opsx:propose` in Claude Code or `$openspec-propose` in Codex.
Revise its plan with `/opsx:update` or `$openspec-update-change`.
Implement it with `/opsx:apply` or `$openspec-apply-change`.
See `README.md` for the complete command table.

### Local workflow rules

Keep these rules here because `openspec update` replaces the generated commands and skills.
Apply them to both agents:

1. **CLI version examination before a proposal.** Run `openspec --version` and
   `npm view @fission-ai/openspec version`. Compare the results. Offer an upgrade if the versions
   differ. Do not upgrade the installed CLI without the user's approval.
   If the registry is unavailable, report that limitation and continue with the installed CLI.
2. **The `ff` alias.** Treat `/opsx:ff`, `opsx ff`, and `$openspec-ff-change` as requests for
   the `openspec-propose` workflow. Prepare the artifacts, then present them for review.
   Start implementation when the user requests the apply workflow.

Keep generated OpenSpec files in `.claude/` and `.agents/skills/` under version control.
After an OpenSpec update, examine the diff and make sure both agents still have the required workflows.
Never run `openspec update --force` in this repository.
A previous forced update removed OpenSpec prompts from `~/.codex/prompts/` and wrote obsolete repository skills.

Specs here describe **aircraft configuration requirements** — what a config must guarantee, and
why — rather than software behaviour. A spec is the right home for a constraint that outlived the
change that discovered it, such as "GPS must not share a UART with the air unit's SBUS output on
the Cube G4 board".

## Style

Match the existing documentation: direct, specific, evidence-first. When something was measured or
tested, say when and what the result was. When a hypothesis was disproven, keep it and say so —
the record of what was ruled out is often more useful than the conclusion.

### Simplified Technical English (ASD-STE100)

Write all new prose in ASD-STE100 Simplified Technical English (STE). This includes replies to the
user, guides, `HANDOFF.md`, specs, OpenSpec changes and commit messages. The documents in this repo
are procedures on hardware with spinning propellers. STE was made for this type of document.

Use these rules:

- Write procedural sentences with a maximum of 20 words. Write descriptive sentences with a
  maximum of 25 words.
- Give one instruction in each sentence. Use the imperative in procedures: "Remove the
  propellers.", not "The propellers should be removed."
- Use the active voice.
- Use only the simple tenses: present, simple past and simple future. Do not use "-ing" forms as
  verbs.
- Write a maximum of 6 sentences in a paragraph. Each paragraph has one topic.
- Start a warning or a caution with the command. Then give the risk: "Remove the propellers
  before you connect the battery. The motors can start without a command."
- Keep the articles "the" and "a". Do not use more than 3 nouns in a row.
- Use each word with one meaning only, as the STE dictionary gives it. For example, write "make
  sure", not "ensure", and "examine", not "check".

Technical names are permitted. These include hardware names (UART, ESC, VTX), Betaflight setting
names (`gps_provider`) and Betaflight mode names.

Do not apply STE to these items. They must stay exact:

- Betaflight CLI lines and the contents of `.txt` config files.
- Lua code and other code.
- Quoted source code, quoted error text and quoted words from the user.

Do not rewrite an existing document in STE unless the user tells you to. When you edit an existing
document, write the new text in STE.
